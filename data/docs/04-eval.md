# LLM 应用评测

## Golden Set
Golden set 是一组带标准答案的评测样本。每条通常包含问题、是否可回答、期望来源、相关 chunk、关键点和期望工具。除了正常问题，必须加入语料外问题，用来检查模型是否会诚实说不知道。样本要覆盖主要主题和失败模式，并随产品迭代维护。

## 检索指标
检索指标只评估召回质量。Recall@k 衡量前 k 个结果里是否包含相关片段；MRR 取第一个相关结果的排名倒数，越靠前越高；nDCG@k 考虑多个相关结果及其排序，并用折损因子降低靠后结果的权重。它们都不需要调用生成模型，便宜且可重复。

## 生成指标
生成指标关注回答本身。Correctness 判断答案是否符合关键点；faithfulness 判断回答是否被检索上下文支持，用来发现幻觉；citation support 检查引用是否真的支撑对应句子。三者结合能区分“答案对但没依据”和“依据充分但答错”等情况。

## LLM-as-judge
LLM-as-judge 用另一个模型按 rubric 打分，通常要求结构化输出、temperature=0，并缓存结果。它便宜、可扩展，但存在位置偏差、长度偏好和自我偏好，也可能解析失败。工程上要提供缺省分数、记录失败原因，并用人工抽查校准。

更具体地，judge 的提示词要写清楚评分维度、每档的含义和输出格式。常见做法是让 judge 输出 JSON，包含分数、理由和引用证据，再用 Pydantic 校验；解析失败时不能直接让评测崩溃，而要记录失败原因并返回一个保守的默认分。pointwise 评分实现简单，适合大批量回归；pairwise 比较更接近人类偏好，但成本翻倍，而且容易出现位置偏差，所以需要交换 A/B 顺序再取平均。judge 还可能偏爱更长、更格式化的回答，或者偏袒同家族模型；可以通过隐藏模型身份、统一长度、加入人工标注样本做校准来缓解。温度设为 0 只能降低随机性，不能消除偏差；同一个样本建议缓存评分，避免重复调用。对于 RAG，judge 最好同时看到问题、检索片段和回答，要求它判断每个关键点是否被片段支持，而不是只判断答案像不像标准答案；这样可以区分“答案正确但引用了错误来源”和“引用正确但答案不完整”。judge 的分数不是绝对真理，应该和人工评分做相关性分析；如果相关性低，优先修改 rubric 和提示词，而不是调阈值。评测报告里建议同时保留原始 judge 输出和解析后的结构化结果，方便回溯；生产环境还要考虑并发、超时、重试和成本上限，避免评测任务把 API 配额打满。

## 任务级指标
任务级指标看端到端表现：任务成功率、工具选择准确率、平均工具调用次数、P50/P95 延迟和单任务成本。成本按输入/输出 token 与价格表估算。它们比单点指标更接近用户体验，适合做版本间的回归对比。

## 回归评测
回归评测把 golden set 跑成固定流程，每次改动后与基线比较。结果应保存为 JSON 和 Markdown 报告，记录模型、提示、检索配置和代码版本。对波动大的指标要看多次运行或设置阈值，避免把随机波动误判为退化。
