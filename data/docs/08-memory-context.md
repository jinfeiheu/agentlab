# 记忆与上下文工程

## 短期记忆
短期记忆是当前会话的消息历史。LangGraph 用 checkpointer 按 thread_id 保存状态，同一 thread_id 的多轮对话可以继续，新建 thread_id 相当于开启新会话。短期记忆会占用上下文窗口，因此长对话需要裁剪或摘要，不能无限追加。

## 长期记忆
长期记忆跨会话保存用户偏好和事实。LangGraph 的 Store 提供 put/get/search 接口，通常按 `("user", user_id)` 命名空间隔离不同用户。Store 可以配置嵌入索引，用语义检索找回相关记忆。长期记忆必须与短期记忆分开，`/new` 只清空当前会话，不应删除长期记忆。

## 记忆写入
记忆写入可以显式调用 save_memory 工具，也可以在每轮对话后自动摘要。写入前要判断信息是否值得长期保存，避免把临时指令、敏感信息或模型猜测写进去。键名要稳定，值要简短；同一事实更新时应覆盖旧值，而不是无限追加。

## 记忆检索
检索记忆时用当前问题作为 query，在用户命名空间内搜索 top-k。结果要拼接成简短上下文，并标明这是历史记忆而非当前事实，避免模型把过期信息当成最新状态。没有相关记忆时返回空，不要用相似度低的结果凑数。

## 上下文窗口
上下文窗口是模型一次能看到的 token 总量，系统提示、历史消息、检索片段、工具结果和本轮输出都要占额度。长对话如果不加控制，最先被挤掉的是早期的用户偏好和关键约束，最后模型可能“记得最近、忘了开头”。因此需要给上下文做预算：明确留给 system、历史、检索和输出的比例，超过预算就裁剪或摘要。

裁剪的常用工具是 `trim_messages`。它按 token 数而不是消息条数计算，可以配置保留开头的 system 消息、保留最近若干条消息，以及是否保留工具调用。实现时要以完整消息为单位，不能把 AIMessage 里的 tool_calls 和对应的 ToolMessage 拆开，否则模型会看到“有调用没结果”或“有结果没调用”的非法历史。token 估算可以用 tiktoken，也可以按字符数近似，但要在模型切换时重新校准。

更激进的做法是摘要：把早期对话压缩成一段要点，替换掉原始消息，再保留最近几轮原文。摘要能显著降低 token，但会丢失细节，而且摘要本身可能引入偏差；所以原始消息应保存在 checkpointer 或数据库中，需要时再取回。上下文裁剪和长期记忆要配合：短期窗口只放当前任务需要的信息，跨会话的偏好放到 Store，按需检索后再注入，而不是把所有历史都塞进 prompt。常见失败包括裁掉了 system 约束、拆散了工具调用对、摘要覆盖了最新事实，以及检索片段太长把输出预算挤没。

## 摘要与压缩
长对话可以用模型生成摘要，把早期内容压缩成一段要点，再放入上下文。工具结果也可以压缩，例如只保留前几百字或提取关键字段，避免一个长网页占满窗口。摘要会丢失细节，因此要保留原始消息在存储中，需要时再检索。
