# RAG 检索增强生成

## RAG 流程
RAG 先准备知识库：加载文档、切分成 chunk、用嵌入模型转成向量并写入向量库。查询时把问题也嵌入，检索最相似的 top-k 片段，再把片段和问题一起交给模型生成回答。它的价值是让模型使用私有或最新知识，并减少凭空编造。

## Chunking
切分决定检索粒度。chunk 太大容易混入无关内容，太小则丢失上下文；常见做法是 300-500 字、重叠 50-100 字。中文要按句号、问号、换行等分隔符切，并尽量保留标题层级。按 Markdown 标题先切分，再对超长小节递归切分，能让每个片段带有章节语义。

## 向量检索
嵌入模型把文本映射成高维向量，语义相近的文本距离更近。检索通常用余弦相似度或内积，返回 top-k。InMemoryVectorStore 适合演示和测试，PGVector 适合持久化与规模更大的语料。向量检索擅长同义表达，但对专有名词和精确关键词不一定敏感。

## 混合检索
单一向量检索擅长同义表达和语义相似，但对专有名词、版本号、错误码这类精确关键词不一定敏感；BM25 正好相反，它依赖词频和逆文档频率，能抓住 `RRF`、`mcp>=1.24,<2` 这样的精确词，却理解不了“断点续跑”和“checkpoint 恢复”之间的语义关系。混合检索把两路召回放在一起，目的是让语义召回和关键词召回互补。

BM25 的核心是：一个词在当前文档中出现得越多、在整个语料中出现得越少，权重就越高；同时用文档长度做归一化，避免长文档单纯因为词多而占优。中文需要先分词，常用 jieba；分词质量会直接影响召回，比如“向量检索”被切成“向量”和“检索”后，匹配行为会变化。工程上通常维护倒排索引，查询时取 BM25 top-k，再和向量 top-k 合并。

融合两路结果常用 RRF（Reciprocal Rank Fusion）。它对每个结果按排名计算 `1/(k+rank)`，再把多路分数相加；排名越靠前分数越高，k 用来平滑头部差异，常见取值是 60。RRF 只依赖排名，不依赖原始相似度，因此不需要把余弦相似度和 BM25 分数归一化，也不会因为两路分数量纲不同而失真。一个结果如果同时出现在两路前列，总分就会明显更高。

实现时可以让向量检索和 BM25 并行执行，各自取较大的候选集（例如 top-20），再用 RRF 融合并截断到最终 top-k。融合后可选地接 LLM rerank，对候选片段做更细的相关性判断。需要监控的失败模式包括：分词错误导致 BM25 召回偏差、向量模型对领域词不敏感、某一路候选过多导致融合结果被单路主导，以及 RRF 的 k 取值不合适让头部过于集中或过于平坦。

## Rerank
Rerank 在粗排之后对候选片段做更精细的相关性打分。可以用交叉编码器，也可以让 LLM 判断片段是否支持问题。它能提升 top-k 的准确性，代价是额外延迟和模型成本，因此通常只对前 10-20 个候选做重排，并做成可配置开关。

## 引用与忠实度
带引用的回答要求模型只依据检索片段，并标注来源，例如 `[来源:文件#章节]`。closed-book 提示会明确要求资料不足时说不知道，不要用参数知识补全。引用既方便用户核查，也是评测 faithfulness 和 citation support 的基础。
